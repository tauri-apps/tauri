Tauri on the Chromium Embedded Framework

Every panel below exercises something tauri-runtime-cef adds that the system webview runtime has no equivalent for. The Rust side of each one is commented in src-tauri/src/.

Chromium … CEF API … runtime style: Chrome

Runtime configuration tauri_runtime_cef::Cef

Configured before the application is built, by passing Cef to tauri::Builder::runtime. Set the environment variable of a row and restart to see it change — the example's README.md lists them all.

Two of those rows are readable back from this page, which is how you can tell the setting reached Chromium and not just the Rust struct:

navigator.languages follows accept_language_list
new AudioContext().state follows command_line_arg("autoplay-policy", …): nothing on this page has been clicked, so a context that starts running is one Chromium did not gate on a user gesture
window.gc follows command_line_args(["js-flags", …]), which is set on the browser process and forwarded to the renderer by Chromium itself

Console messages on_console_message

The renderer's console output, observed in Rust without DevTools being open. The handler runs on CEF's UI thread and does not suppress the message: CEF still logs it as it normally would.

Frame lifecycle on_frame_event

Native CEF notifications for every frame of this browser, child frames included — which Tauri's portable navigation callbacks do not report. A CEF-owned popup is a different browser and never shows up here.

Chrome accelerators allow_chrome_commands

A Chrome style browser keeps its whole accelerator table live even hosted as a child view with no browser UI, so Ctrl+N would open a real Chrome window next to the app's and Ctrl+H would load Chrome's history page over the app's UI. The runtime swallows those families by default; tick the ones this window should keep.

  • Zoom is not a group: it follows zoom_hotkeys_enabled, which defaults to false. Ctrl+mouse wheel zooms either way.
  • Alloy style has no Chrome UI at all, so its accelerator table is not live to begin with.

DevTools protocol send_dev_tools_message

Chrome DevTools Protocol requests against this webview's browser, with the request id taken from allocate_devtools_message_id(). Every observer on the browser sees every result, so a hardcoded id can consume somebody else's answer.

Native state with_cef_webview

The native CEF handle, on CEF's UI thread. The snapshot is sampled immediately before the closure runs and is never refreshed, so it says what was true at that instant and nothing about now. 

click to sample
  • browser is read from the raw cef::Browser the handle exposes, so it is live CEF state rather than part of the sampled snapshot.
  • popups lists the CEF-owned browsers this one opened — open one from the popups panel and sample again.
  • documentAdmitted is false unless every known frame is attached and the load has finished, and selectedByItsDocument is Webview::for_document handed that document's own token back.
  • dialogs only ever says what CEF observed of a native JavaScript dialog, and only its kind and whether Chromium has a browser-side handler for it — never the message or the prompt value, which are page content. known: false means nothing was observed, never that no dialog is up.
  • sameNativeWindowAsPreviousSample compares NativeWindowTokens, not labels: a window closed and rebuilt under the same label reports false. Both child webviews of a multiwebview window report the same one, because they share a window.

Popups AsCefWindowOpener

CEF hands the opener's main-frame URL straight to the new-window callback, so it can be read without a blocking webview getter — which on this runtime can deadlock the UI thread. The handler answers with a real Tauri window, unless the URL is fragmented #cef-owned: it then answers NewWindowResponse::Allow and CEF opens a browser of its own, which has no Tauri label and shows up under Webview::popups() instead.

  • The Tauri popup is sampled by its label in the native state panel like any other window. The CEF-owned one has no label, so it is observed under popups of this window's own sample, where it also selects itself back out of the family by its own document token.

Child webviews WebviewBuilderCefExt

Everything WebviewWindowBuilderCefExt adds to a window-plus-webview builder, on the tauri::webview::WebviewBuilder of a window that hosts several. It follows Tauri's multiwebview API behind the unstable feature. The window opens with two sibling browsers side by side, and the runtime style is a per-browser choice: Chrome on the left, Alloy on the right.

  • Both children report their console output and their frame lifecycle to the panels above, tagged with their own webview label.
  • Both allow ChromeCommandGroup::History, but only the Chrome style one has an accelerator table for it to apply to.

Permissions on_permission_request

Answered in Rust, before Chrome's own prompt. Chromium consults the prompt only while the stored content setting still says "ask", so most decisions reach the handler once per origin and then persist to the on-disk profile — restarts included. Camera and microphone are the exception and are asked every time.

Deep links deep_link_schemes

A second launch of a running app reaches Chromium's process singleton, which relays the new process's command line — a command line CEF has by then cleared. The runtime puts the deep link URL back on it, so the URL arrives here as RunEvent::Opened.

  • macOS: open tauri-cef-example://hello
  • Linux and Windows: run the built executable again with tauri-cef-example://hello as its argument.
